# libpinesy

libpinesy is the core library of the Pi/Ne-Sy front ends. It holds every rule the front ends share, so each front end holds only its UI:

- the machine catalogue, built from the engine's driver list
- configurations: the command line model, its edits, and checking it with the engine
- `.pinesy` files
- the starting configuration of a new machine
- the options and search paths every run starts with
- the settings schema, and the options settings add to a run
- the machine window's size
- the headless command line that Copy Command Line gives, quoted for zsh
- headless mode
- the build's identity, and when an app shows that it is out of date

The rules are the ones `../app/README.md` describes. The core calls the engine, `libmame_pinesy`, through its C interface `../engine/include/pinesy.h`. It opens no windows.

The core is C++20. Its C interface is `include/pinesy_core.h`. That interface wraps the C++ interface in `include/pinesy_core.hpp`.

Every front end uses the core:

- The macOS app (`../app`) imports `pinesy_core.h` into Swift. `../app/build.sh` compiles the core's sources with `clang++` into `libpinesy.dylib` and bundles it in `Contents/Frameworks`, next to the engine.
- The GNOME app (`../gtk`) uses the C++ interface, and the KDE app (`../kde`) the C interface. Their CMake builds build the core from `CMakeLists.txt`.

To build it and run its tests, see [docs/build-macos.md](../docs/build-macos.md) or [docs/build-linux.md](../docs/build-linux.md).

## The interface

`pinesy_core.h` documents every function. In outline:

- **A core.** `pinesy_core_create(resources_folder, default_data_folder)` makes one, and `pinesy_core_destroy()` frees it. The two folders are the platform's part. The resources folder holds the bundled ROM sets in its `roms` folder, and MAME's search folders (`hash`, `plugins` and others). On macOS it is the bundle's `Resources` folder. The default data folder is `~/Library/Application Support/Pinesy` on macOS and `$XDG_DATA_HOME/pinesy` (by default `~/.local/share/pinesy`) on Linux.
- **Text.** A command line is a JSON array of strings: the driver, then options, as in a `.pinesy` file. Calls that return `char *` return text that the caller frees with `pinesy_core_free()`. They return `NULL` when an argument is `NULL` or is not the JSON it must be.
- **Settings.** The front end stores the settings and gives them to the core with `pinesy_core_set_settings()`, as JSON with `romFolders`, `dataFolder`, `debugger` (`windows` or `gdbStub`), `gdbPort`, `startPaused`, `piGdbPort`, `updateChecks` and `ignoredBuild`. A missing or unusable value takes its default.
- **Paths.** `pinesy_core_fixed_options()` gives the options every run and every check starts with: `-noreadconfig`, `-rompath`, MAME's search paths, the folders MAME writes, and `-skip_gameinfo`. `pinesy_core_rom_folders()` gives the ROM folders in search order. `pinesy_core_create_folders()` creates the folders MAME writes. `pinesy_core_nvram_folder()` gives the folder MAME keeps a configuration's NVRAM in, and `pinesy_core_clear_nvram()` deletes the NVRAM MAME saved for the configuration's driver, and nothing else.
- **The catalogue.** `pinesy_core_catalogue()` gives the machine list in sections. `pinesy_core_search()` finds machines by name, maker, model or ROM variant name. `pinesy_core_machine_for_driver()` gives the machine a driver belongs to. `pinesy_core_starting_arguments()` gives the command line a new configuration for a driver starts with.
- **Configurations.** `pinesy_core_new_configuration()` starts a configuration for a machine. `pinesy_core_set_driver()`, `pinesy_core_set_rom()`, `pinesy_core_set_slot()`, `pinesy_core_set_card_rom()` and `pinesy_core_set_media()` edit one. Each edit except `pinesy_core_set_media()` checks the result with the engine and removes the options the machine no longer has, as `pinesy_core_normalise()` does.
- **Checking.** `pinesy_core_summary()` asks the engine about a configuration and gives what the configuration window shows: the machine, its models and ROMs, a row for each slot and each media device, the engine's errors and warnings, mandatory media with no file, media files that are not there, SD card images that MAME's SD card cannot use, whether the machine takes a mouse, and whether it can run. A configuration with such an image cannot run. `pinesy_core_sd_card_problem()` gives the reason for one image, so a front end can refuse it when it is chosen.
- **Files.** `pinesy_core_read_document()` reads a `.pinesy` file's text, with its window size, mouse setting and Pi pause setting, and `pinesy_core_write_document()` writes it.
- **The machine window.** The engine's `size` callback gives the frame's size in device pixels. `pinesy_core_window_size()` turns it into the window's content size in logical units, from the configuration's window size (`PINESY_CORE_WINDOW_FULL_SCREEN`, `PINESY_CORE_WINDOW_FIT` or a magnification of 1 or more), the screen's device pixels per logical unit, and the room the content has on the screen. Full screen gets the Fit size, which the window has when it leaves full screen. Each front end measures the screen and calls it when a machine starts and when the frame's size changes. `pinesy_core_window_full_screen()` says whether the window opens in full screen. The configuration window's choices come from the core too: `pinesy_core_window_choice()` gives the choice that shows a window size (Fit, Full screen, 1x to `PINESY_CORE_WINDOW_LISTED_MAGNIFICATIONS`, or `PINESY_CORE_WINDOW_CUSTOM` for a larger magnification), and `pinesy_core_window_size_for_choice()` gives the window size a choice, or a number entered for Custom, sets.
- **Runs.** `pinesy_core_run()` runs a configuration with `pinesy_run()`, with the fixed options first, then the configuration, the mouse option, the debugger options from the settings, and last the MAME options of Pinesy's switches. The front end passes the summary's `mouse` and the configuration's mouse setting. For a machine that takes a mouse, the mouse option is `-mouse` with the setting on and `-mouse_device none` with it off; any other machine gets none. `pinesy_core_copy_command_line()` gives the headless command for a configuration, quoted for zsh, with the same mouse option. A run with the debugger has Pinesy's switches (`run_switches()` in `pinesy_core.hpp`): `--paused` from the settings' `startPaused`, and `--paused-pi` from the configuration's Pi pause setting when it has a Pi SD card. A run gives MAME `-pi_gdb_wait` for `--paused-pi`, and tells the engine `pinesy_set_start_paused()` for `--paused`. The copied command line has none of the switches.
- **Recent configurations.** Each front end keeps its list of recent `.pinesy` files in the platform's own store. `pinesy_core_recent_configurations()` gives the ones to show: the files that exist, newest first, each once, at most `PINESY_CORE_RECENT_LIMIT`, with each file's name and folder. `pinesy_core_note_recent()` gives the list to keep after a configuration is opened or saved, for a front end that keeps the list itself. `pinesy_core_launch()` gives what a launch opens: the files it was given, the recent configurations when there is at least one, or a new configuration. `pinesy_core_restorable()` says whether a configuration window is restored at the next launch: only one with a machine.
- **Headless mode.** `pinesy_core_headless()` runs the executable's arguments as headless mode does: Pinesy's switches before the first `--`, MAME's command line after it. `pinesy_core_video_none()` and `pinesy_core_opens_debugger_windows()` tell the front end whether MAME needs a window, and whether MAME's debugger windows will open.
- **Updates.** A build that CI publishes has its identity in `build-identity.json` in its resources folder: a JSON object with `track` (`ci`, `nightly` or `release`), `version` and `kind` (`macos`, `flatpak` or `deb`). The core reads it when it is made. A local build has no such file. `../app/build.sh` writes it from `PINESY_BUILD_TRACK` and `PINESY_BUILD_VERSION`, the Linux apps' install writes it from the CMake cache variables `PINESY_BUILD_TRACK`, `PINESY_BUILD_VERSION` and `PINESY_BUILD_KIND` (`../cmake/PinesyInstall.cmake`), and `../cmake/make-deb.sh` writes it into a Debian package. `pinesy_core_build_identity()` gives it. `pinesy_core_update_checks()` says whether the app looks for updates: a CI build with the settings' `updateChecks` on. Each app finds the newest build in its own way and asks `pinesy_core_update_notice()` whether to show the out-of-date notice: not when the build is the settings' `ignoredBuild`, and only for a newer build, by `pinesy_core_compare_versions()` (Sparkle's comparison), or, for a Flatpak, by a commit other than the one that runs. `pinesy_core_flatpak_ref_url()` gives the app's ref file in the track's Flatpak repository, from `/.flatpak-info`, and `pinesy_core_flatpak_newer_commit()` gives the commit in it when that is not the running commit. `pinesy_core_update_texts()` gives what the notice says, and `pinesy_core_update_choice()` applies a choice to the settings for the app to store. `pinesy_core_appcast_url()`, `pinesy_core_apt_packages_url()` and `pinesy_core_apt_newest_version()` give Sparkle's appcast, the track's apt index, and the newest version of a package in that index.

Calls that ask the engine, which the header marks, run on the main thread and never while a machine runs.
